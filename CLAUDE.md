# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

DomainBenchmark is a Nextflow DSL2 pipeline for benchmarking domain-domain interaction (DDI) prediction methods. Built from the `nf-core/tools 4.0.2` template. For each database it runs feature extraction → ML classifiers (NN, RF, SVM) → MultiQC evaluation (the graph models KGIDDI/DDIParsimony are deprecated, still wired but off everywhere), then aggregates across databases. A database ships one or more `test_<variant>` splits (currently an in-distribution 1:1 set, `test_matched_1_1` or for `random` `test_uniform_1_1`, and a 1:10 set with the same positives and uniform negatives, `test_uniform_1_10`; unseen families come from `minimal_leakage`, external data from `external_test`) or a single `test`; all are scored by the same trained models and reported as separate datasets.

## Common commands

```bash
# full run across every database in the samplesheet (cluster: executor/queues/
# workDir/GPU clusterOptions all come from the -c config, not from this repo).
# A samplesheet input needs --embeddings and --structures for the published and structure features.
nextflow run . --input my_samplesheet.csv --embeddings /path/to/domainsplit/results/embeddings --structures /path/to/domainsplit/results/structures/structures.h5 -c daisybio.config -profile apptainer,gpu,keep_work -resume

# same, straight off a domainsplit output directory
nextflow run . --input /path/to/domainsplit/results/databases -c daisybio.config -profile apptainer,gpu,keep_work -resume

# stub run (smoke test)
nextflow run . -profile test,singularity -stub-run

# without the graph models
nextflow run . --input /path/to/domainsplit/results/databases -c daisybio.config -profile apptainer,gpu,keep_work --skip kgiddi,ddiparsimony,kgiddi_random

# lint
nf-core pipelines lint --dir .

# nf-test
nf-test test tests/default.nf.test tests/launch_checks.nf.test

# S-12 staging regression: two stub runs, appending a feature must re-run only its own and the _all models
tests/stub_resume_staging.sh
nf-test test tests/launch_checks.nf.test   # launch-time failures, no tasks run

# W-6 seeds: --seeds 42 then 42,43 resumed; seed-dependent tasks double, the rest do not, seed-42 models stay cached
tests/stub_seeds.sh

# W-10 1:1 -> 1:k wiring: a copy of the fixture with ratio-named test splits; only 1:10 EVAL_ONE stages the 1:1 reference
tests/stub_test_set_shift.sh

# W-15 identity vocabulary staging: touching a copy's validation.sqlite3 re-runs every identity extraction, aacomp stays cached
tests/stub_identity_vocab.sh

# unit tests (CI: .github/workflows/pytest.yml). The results-tree invariants
# in test_invariants.py run only with DOMAINBENCHMARK_RESULTS=<an --outdir>;
# CI does not set it, so run them by hand before a release.
PYTHONDONTWRITEBYTECODE=1 python -m pytest -q -p no:cacheprovider tests/python
```

`--input` takes either a samplesheet CSV or a directory. Samplesheet schema (`assets/schema_input.json`): array of `{id, db_path}` rows. Directory form: every immediate subdirectory holding a `train.sqlite3` is a dataset named after the directory (what domainsplit publishes under `databases/`). Either way each database directory must contain `train.sqlite3`, `validation.sqlite3`, and one or more `test*.sqlite3`. Skip stages via `--skip aacomp,kgiddi` (comma-separated, matches feature, ML model or graph model names).

Everything that can be checked before a task runs is checked at launch, in `PIPELINE_INITIALISATION` (`validateDatasets()` / `validateModelParams()`): samplesheet rows (non-empty `db_path`, whitespace-free `id`), unique dataset ids, unique run labels, `--mqc_order` names against the run labels, every `machine_learning_models` / `graph_models` / `machine_learning_features` / `--skip` token against what exists, no feature listed twice, no structure encoder in `machine_learning_features`, every `structure_informed_features` entry listed in `published_features`, no list param passed as `''` or without a value (Nextflow turns both into Boolean `true`; disable a list with `none`), and the keys each enabled ML model reads from `assets/<Model>.json` (some, like `retrain_epochs`, are read only at refit, after the whole grid search). Each of these used to surface late or not at all — an unknown model name trained nothing and the run "succeeded" without a report. `assets/schema_input.json` is deliberately not wired into the `input` schema entry: `--input` may be a directory, and relative `db_path`s resolve against projectDir here but against launchDir in nf-schema.

What needs the data is checked by **`PREFLIGHT`** (`bin/preflight.py`, one task per database, beside `DDI_EXTRACTION`), and NN/RF/SVM and `SASA_CACHE_SHARD` are joined on its output — so a database that would crash `EVALUATION` or `ENRICHMENT` fails in minutes, not after ~15 h of training (training and test scoring share one task, so a late failure there also discards the training). Every check calls the function the late stage calls, so the two cannot diverge: PPI scores coerce (`load_data_gm.load_ppi`, which every `EVALUATION` runs); every feature combo, `_all` included, resolves ≥ 1 membership instance pair on every split by key presence (`verify_embeddings.read_pairs` + published h5 keys + structure coverage), with both classes at DDI level on train/validation (a single-class test split only warns); every complex parses (`structure_utils.iter_structures`), with every CYS carrying SG when `disulfide_bond_count` is enabled and every LYS/ARG/ASP/GLU its charged N/O when `salt_bridge_count` is (their own `encode`), and every non-GLY residue a CB when a CB-based encoder (`contact_map`, `patch_*`) is (`structure_utils.cb_coords`); every sequence an enabled sequence encoder reads cleans (membership instances only; an unused bad sequence fails nothing) (`embeddings.clean_sequence` over the encoder's own `SEQUENCE_QUERY` / `MIN_SEQUENCE_LENGTH`); with `--metadata`, every test DDI gets a metadata row (`create_metadata.build_table` + `eval_enrichment.join_predictions`); and the post-training toolchain loads (multiqc on PATH, the evaluation/enrichment modules import). Not checkable up front: GPU/node faults, prediction OOM (no memory estimate, deliberately — too heuristic), non-finite model output, a MultiQC crash on valid input, and encoder-specific failures that need the computation itself (no solvent-accessible atom, a non-finite structure vector).

**`-resume` does not see edits to imported helpers.** Nextflow hashes only the `bin/` scripts named in a process's command line, so editing `machine_learning.py`, `determinism.py`, `bin/features/*.py`, `eval_multiqc_functions.py`, `load_data_gm.py`, `kgiddi_functions.py` or `ddiparsimony_functions.py` and resuming reuses the cached outputs of the tasks that import them (verified with a two-file mini pipeline). Accepted, not fixed: after editing a helper, run without `-resume` — or delete the affected tasks' work dirs — for any stage whose outputs you want regenerated. The same holds for the input databases: `DDI_EXTRACTION`, `PREFLIGHT` and `FEATURE_EXTRACTION_ONE` take the database *directory* as input, and a directory is hashed by its own metadata, not its children, so editing a split `.sqlite3` in place and resuming can reuse their stale outputs, while `identity` (which stages train/validation as files of their own) reruns. After editing a database in place, run without `-resume`.

Python deps managed via conda — `environments/general.yml` (extraction/RF/graph/eval) and `environments/ml.yml` (conda-forge PyTorch CUDA 13.4 + cuML for NN training — one conda solve, no pip; Dockerfiles in `docker/` install these files; see `environments/README.md`). No `pyproject.toml` / `requirements.txt`.

## Architecture

### Top-level layout
- `main.nf` — a typed `params { }` declaration block, then the entry. `PIPELINE_INITIALISATION` → `DAISYBIO_DOMAINBENCHMARK` (the science workflow: `PER_DB_BENCHMARK` scattered per DB → `AGGREGATE_EVAL`) → `PIPELINE_COMPLETION`. There is no pipeline-level MULTIQC process and no software-version collection: the report is built by `bin/eval_multiqc.py` / `bin/combine_eval.py`, which write their own MultiQC configs.
- `subworkflows/local/per_db_benchmark/main.nf` — scatter: `DDI_EXTRACTION` → `FEATURE_EXTRACTION` (fan-out feature × split) + `VERIFY_EMBEDDINGS` (per db, for `params.published_features`) → `NEURAL_NETWORK` + `RANDOM_FOREST` (per-feature singletons + up to two concatenations, `all` and `all_seq`, gated by `params.machine_learning_models`) + `GRAPH_MODEL` → `EVAL_ONE` (per-prediction) → `EVALUATION` (per (db, test variant) MultiQC reduce). `runLabel()` (defined in the utils subworkflow, so launch-time validation can use it) builds the `<db>_<variant>` run name used downstream. The EVALUATION group uses `groupTuple(size:)` with the per-variant model count (× n_seeds for the ML models), so each (db, variant) reports as soon as its own models finish; a (db, variant) that receives no predictions at all is an error, not a silent drop.
- `subworkflows/local/aggregate_eval/main.nf` — runs `COMBINE_EVAL` across per-DB reports to produce `results/evaluation/ddi_report.html`.
- `subworkflows/local/utils_nfcore_domainbenchmark_pipeline/main.nf` — nf-core boilerplate (initialise, completion) plus `discoverSplits()` / `datasetTuple()`, which turn a database directory into `meta.splits` / `meta.tests`.
- `nextflow.config` — single source of truth for `graph_models`, `machine_learning_models`, `machine_learning_features`, `published_features`, `structure_informed_features`, `large_features`, `embeddings`, `min_embedding_coverage`, `ppi_score_cutoff`, `mqc_order`, `skip`, `outdir`, profiles.
- `conf/{base,test,test_full,modules}.config` — layered config. `conf/base.config` carries retry strategy and per-label resources. There is deliberately no executor profile: executor, queue, `workDir` and GPU `clusterOptions` come from the institutional config passed with `-c` (e.g. `daisybio.config`), which keys on the `process_gpu` label. `conf/base.config` therefore must never mention a queue. NN/RF memory/time are sized per task from `params.large_features` in `conf/modules.config` (`withName` beats `withLabel`), which is what replaced the old `process_gpu_small`/`process_gpu_large` labels. Graph models carry `process_graph` (12 cpus, 160 GB × attempt, 24 h). That label sat dead for a while — it was defined here while `modules/local/graph_model/main.nf` still declared `process_high`, so every graph model silently ran at 72 GB and a cluster run lost five kgiddi/kgiddi_random tasks to exit 137 and two ddiparsimony tasks to a `BrokenProcessPool`. Its cpu count is deliberately not raised: both graph models fan `--threads task.cpus` into a `ProcessPoolExecutor`, so each extra cpu is another worker holding its own copy of the interactome, and memory demand rises with cpus.
- `assets/<ModelName>.json` — per-model hyperparameter grid + search config. Filename must match `model_name` and the Python script in `bin/`.
- `modules/local/<stage>/main.nf` — Nextflow process defs (`ddi_extraction`, `preflight`, `feature_extraction`, `verify_embeddings`, `neural_network`, `random_forest`, `graph_model`, `evaluation`).
- `bin/` — Python entrypoints invoked by modules (`neural_network.py`, `random_forest.py`, `run_graph_models.py`, `kgiddi.py`, `ddiparsimony.py`, `extract_features.py`, `verify_embeddings.py`, `eval_one.py`, `eval_multiqc.py`, `combine_eval.py`, `load_data_gm.py`). Auto on `PATH` from Nextflow.
- `bin/determinism.py` — `seed_everything(seed)` (seeds `random`/`numpy`/`torch`, kills cuDNN autotuning, asks torch for deterministic kernels) and `derive_seed(seed, *tokens)` (stable child seed for a worker, keyed on its own identity rather than completion order). Every entrypoint calls it. `PYTHONHASHSEED=0` and `CUBLAS_WORKSPACE_CONFIG` are set in the `env` scope of `nextflow.config` — they must exist before the interpreter starts.
- `bin/features/` — feature encoders (`aacomp`, `aaencode`, `identity`, `embeddings`, `protdcal`). Every encoder is `extract_features(conn, out_file, seed)` — the seed is part of the ABI whether or not the encoder draws from it, so a sampling encoder cannot be added without one. New *extracted* feature = new file here + entry in `params.machine_learning_features`; key the HDF5 group by Pfam accession via `embeddings.DOMAIN_KEY_SQL` + `embeddings.DOMAIN_JOIN_SQL` and the dataset by instance via `embeddings.INSTANCE_KEY_SQL` / `embeddings.write_instance()`. Heavy ones go in `params.large_features`. Sequence encoders run every sequence through `embeddings.clean_sequence()`: residues outside the standard 20 are stripped, and a NULL, empty or too-short-after-stripping sequence **fails** the task naming the instance (aacomp used to divide by zero, aaencode silently returned an all-zero vector). `write_instance` rejects a key containing `/`, which HDF5 would turn into a nested group. `protdcal` extracts only the `ddi_split_membership` instance pairs and runs its E-state operator along residue positions; note that under its current mean aggregation that operator cancels exactly (the kernel is symmetric), so the feature reduces to length-weighted mean properties — see its docstring. There are no embedding encoders any more: domainsplit stopped storing BLOBs in SQLite, so `protein.*_per_residue` and `domain_protein_map.*_per_domain` are gone from the schema and the `esm3_*`/`esmc_*`/`prott5_*` extractors that read them were deleted with the columns.
- `docker/` — image definitions. One image per environment, referenced directly in each module's `container` directive.

### Data flow
1. Input: samplesheet of `{id, db_path}` or a `databases/` directory. Each database dir contains `train.sqlite3`, `validation.sqlite3`, and one or more `test*.sqlite3` (tables: `domain`, `domain_go_terms`, `domain_domain_interaction`, `protein`, `protein_go_terms`, `protein_protein_interaction`, `domain_protein_map`, `ddi_split_membership`).
2. `DDI_EXTRACTION` → SQL → `<split>.csv`, `<split>_sources.csv` and `<split>_instances.csv` (the domain-instance pairs `ddi_split_membership` assigns to that split — what the ML loader instantiates, instead of a cross-product). Every one of them joins `domain` and reports **`pfam_id`**, never `domain.id`; see "The domain key" below. Output is `ORDER BY`ed so the CSV bytes do not depend on the query plan. The task **fails** on inconsistent input rather than dropping rows: `ddi_split_membership` holding more than one `(method, split)` (domainsplit's `SUBSET_SPLIT_DB` copies exactly one), a membership row whose instance or DDI is missing, an instance pair whose domains do not match the DDI's two sides, or a `negative` that is not integer 0/1 (the column is untyped, and `NOT 'True'` is 0 in SQLite — a text boolean would silently flip labels), a family pair stored in both orientations with different labels, or a `ddi_split_membership` split that differs from the file name (`validation.sqlite3` must say `validation`).
2a. `PREFLIGHT` (per db, in parallel with `DDI_EXTRACTION`, which is why it reads the split databases rather than the CSVs) — see the launch-checks paragraph above. Writes `preflight.txt`; its output gates every ML input and the SASA build.
3. `FEATURE_EXTRACTION` (fan-out per feature × split) → one `<feature>__<split>.h5` per task under `results/<db>/data/`. The flat name carries the layout; each NN/RF/SVM task stages only its own combo's files (`comboFiles()` in `per_db_benchmark`, exact-name match on `<feature>__<split>.h5` / `<feature>.h5`) into `features/` and `machine_learning.py:resolve_feature_file` resolves them — staging the whole set put every feature into every model's task hash, so appending one feature reran every model on `-resume`. The per-db `groupTuple` of `FEATURE_EXTRACTION` output is sized with `groupKey(db_id, n_splits × (n_seed_free + n_seeded × n_seeds))` (see "Several seeds" below), so one database's models do not wait for another's features. HDF5 layout is `h5[pfam_id][instance_key]` — keyed by Pfam accession (see "The domain key") and instance-level, because one protein can carry two instances of the same family. There is deliberately no staging process in between: the old `STAGE_FEATURE_DIR` cost a scheduled job per (db, feature) to run `cp`, and on a node that cannot loop-mount the SIF, singularity unpacked the whole image first and blew through the label's walltime (exit 140). (`resolve_feature_file` used to accept a `features/<feature>/<split>.h5` tree as well; that branch went when the process that built it did.)
3b. `VERIFY_EMBEDDINGS` (per db) for every `params.published_features` entry. These are not extracted at all: domainsplit publishes one `<model>_domain_embeddings.h5` per **run** under `--embeddings`, and the process gates it against the split databases before renaming it to `features/<feature>.h5` for `resolve_feature_file`'s second layout (`publishedEmbeddingFile()` tries `<feature>.h5`, then `<feature minus _embeddings>_domain_embeddings.h5`, so `esm3_structure_embeddings` reads `esm3_structure_domain_embeddings.h5`). See the reproducibility note below for why the gate exists. Published embeddings computed with structure input are listed in `params.structure_informed_features` (default `esm3_structure_embeddings`, a subset of `published_features`, checked at launch): they run as a singleton and inside `_all` but stay out of `_all_seq`.
3c. **Structure features** (`params.machine_learning_features_structure`, **off by default** since 2026-11-17: domainsplit models complexes for 62–79 % of positives but 0–13 % of negatives, so coverage nearly is the label — re-enable when domainsplit models negatives at the same rate; with them off, `_all` holds none) are computed on the AF3 complex of each instance pair, read from domainsplit's `structures.h5` (`--structures`; left unset it is derived as `structures/structures.h5` beside `--input`'s `databases/`, like `--embeddings`). Its layout is domainsplit's: group `<pfamA>_<pfamB>`, dataset `<instA>__<instB>` = gzip'd two-chain PDB, keyed in the membership row's orientation. `SASA_CACHE_SHARD` (× `params.sasa_cache_shards`, sha256-assigned) + `MERGE_SASA_CACHE` run Shrake-Rupley once per complex over every database; each structure feature then runs through `FEATURE_EXTRACTION_ONE` like any other, reading the cache. Every encoder is `encode(complex, **params)` wrapped by `structure_utils.make_extractor`, and all go through one iterator, `structure_utils.iter_structures`, which (a) **fails** if `ddi_split_membership` lacks `has_structure`, if a `has_structure = 1` row has no complex in either orientation, or if a split has no structure at all, (b) looks the complex up orientation-agnostically (domainsplit sorts families numerically but instance ids as strings, so the stored orientation is not guaranteed) and swaps chains so `cx.first` is always the row's instance a, (c) prints pair- and DDI-level coverage per label. A complex must have exactly chains A and B, standard residues and a full backbone, or the task fails. The interface encoders share two definitions in `structure_utils`: an **interface residue** is one whose SASA drops by more than 1 Å² from chain alone to complex (`interface_residues`, the ΔSASA definition `aacomp_interface` and the BSA features already used), and a residue is placed at **CB** (CA for GLY; a non-GLY residue without CB fails, `cb_coords`). On them: `contact_map` = binary CB–CB ≤ 8 Å maps (CASP convention; intra-chain per chain + inter-chain, 29 + 29 + 35 = 93); `patch_max_size_*` = largest connected patch of interface residues linked by CB–CB ≤ the variant's distance, `[first chain, second chain, overall]` (3); `patch_mean_contacts_*` = inter-chain interface CB–CB pairs ≤ the distance per interface residue (1); `charge_map`/`hydrophobic_map` = CCI/HCI over the first × second chain interface residues (35, zeros without an interface on both chains); `salt_bridge_count` = inter-chain residue pairs with LYS NZ / ARG NE,NH1,NH2 ≤ 4.0 Å of ASP OD1,OD2 / GLU OE1,OE2 (HIS excluded; a missing charged atom fails). `encode_matrix` carries no size term (the old `log1p` of the chain length made the maps "length plus noise"), bands on residue numbers, and a rectangular map's transpose is a permutation of its vector. These replaced CA–CA definitions that were degenerate (`patch_max_size_10A` was lenA+lenB for every fixture complex; `salt_bridge_count`'s CA–CA ≤ 5.5 Å caught 1 of 89 real salt bridges). Output is the interaction layout protdcal uses, written in **both** orientations (chain-ordered features swap halves) and marked `attrs["layout"] = "interaction"`, which is how `load_embedding_data` recognises it (protdcal writes the attribute too; a file without it is treated as interaction layout by name only for `protdcal`, with a warning). A DDI without any structure-covered pair resolves nothing in a combo containing a structure feature, so such combos — `_all` included, by decision — score the structure-covered subset only; `_all_seq` is the full-population counterpart. Parameterised variants (`k_closest_distance_5k`, `patch_max_size_7.5A`, …) are entries of `assets/feature_variants.json` (name → module + params), resolved in `PER_DB_BENCHMARK` and passed as `--module/--params`. **Scientific caveat:** positives come from PDB co-crystals that may have been in AF3's training data (PDB cutoff 2021-09-30) — i.e. read every structure result as "with AF3 that may have seen the positives" — so interface features (BSA, contacts, clashes, patches) partly measure AF3 recall rather than predict an interaction. Ported from the student branch `enrichment` (Chiara, git `chialtho`); `struct2graph` (untrained network, per-split vocabulary), `adjacency_matrix` and `interface_area` (= `bsa_structure`/2) were dropped.
4. `NEURAL_NETWORK` / `RANDOM_FOREST` / `SVM` consume `.h5`, grid-search via model JSON (fit on train, scored on validation), then score every test split → `predictions_<variant>.parquet` under `results/<db>/nn_output/`, `results/<db>/rf_output/` and `results/<db>/svm_output/`. The unit of everything is the **canonical DDI**, not the instance-pair row:
   - Class balancing (train downsample, RF oversample) runs *after* feature resolution on canonical DDIs, keeping both orientations and every instance row of a kept DDI together. It used to sample oriented tuples before resolution, which left "balanced" sets at e.g. 60:10 rows / 1000:1937 DDIs and stripped most negatives of one orientation. Validation is **not** balanced (`balance_positive_and_negative_interactions_opt_set: false` in every model JSON; `true` still works and is recorded as `selection.validation_balanced`): selection, NN early stopping and the operating points all see every validation DDI the combo resolves.
   - Hyperparameters and the balance method are selected on **DDI-level average precision** (`machine_learning.DDIAveragePrecision`: `_aggregate_to_ddi_level` — mean over instance rows and orientations — then AP), the same aggregation the operating points and evaluation use.
   - **Operating points** (`machine_learning.threshold_at_fpr` / `threshold_at_prior` / `universe_prior`), derived after the refit from the DDI-aggregated validation scores — the exact float32 array `predict()` compares against. Primary `fpr0.01`: the smallest candidate threshold (every distinct validation score, plus one just above the maximum) whose validation false-positive count is ≤ the integer budget `floor(0.01·n_neg)`; tie-aware (`score >= t` counts every tied negative), never `np.quantile`, `resolvable` only with ≥ 100 negatives. Secondary `universe_prior`: the MCC optimum at prevalence π = positive train DDIs / possible pairs of train domains (self-pairs in the universe only if `train.csv` holds a same-family DDI), computed from `DDI/train.csv` so it is one value per database whatever a combo resolves; a scenario (catalogue density), `resolvable` only when the optimum has ≥ 1 validation false positive. MCC-argmax at validation's ~1:1 balance (`_tune_threshold_mcc`) is gone. `predicted_interaction` is labelled at `fpr0.01`, `predicted_interaction_prior` at `universe_prior` (ML parquets only; the graph models have no such column). Both thresholds are applied unchanged to every test split. `EVAL_ONE` stages the model's `model_parameters.json` beside each prediction (W-7) and reports both points.
   - Every NN fit (grid candidates and refit) uses `torch.optim.Adam` (skorch's default was SGD), recorded as `optimizer` in `model_parameters.json` (null for RF/SVM). Candidates and refit both train on all of train and early-stop on the validation split (`predefined_split`, `EarlyStopping(patience=5, load_best=True)`); each candidate receives only the `PredefinedSplit`'s train rows from `RandomizedSearchCV`, so validation rows never enter its training data. `grid_search_epochs` (100) and `retrain_epochs` are caps. The old row-level `ValidSplit(0.2)` put one DDI on both sides and kept the last epoch.
   - Every split load prints DDIs requested / resolved / dropped by reason; a non-finite (NaN/inf) row is dropped, and all-non-finite raises.
   - Both models probe CUDA (`machine_learning.probe_cuda`) and exit 140 on an unusable GPU unless `--allow_cpu` (`params.allow_cpu_ml`). TF32 is off in code as well as in the container (`NVIDIA_TF32_OVERRIDE=0`), so conda and container runs agree. NN candidate failures are fatal (`error_score="raise"`), as RF's already were.
   - `model_parameters.json` records `features` (in concat order) and `seed` next to the chosen parameters and balance method, a `selection` block (metric, split, `validation_balanced`, n_pos/n_neg/n_same_family, `score_by_balance_method`), `primary: "fpr0.01"` and the `thresholds` block (both points with their validation rates, counts and `resolvable`), so an `_all` run is identifiable. There is no scalar `threshold` key, and `run()` / `--predict-only` **fail** on a `model_parameters.json` without a valid `thresholds` block (no legacy read path: results from before this change are retrained, not re-labelled). `--predict-only` fails unless `--features` equals that saved `features` list, in order (an artefact without `features` fails). A missing `<split>_instances.csv` fails; there is no cross-product fallback. DDI aggregation fails on a NaN/inf score, a non-0/1 label, or a pair labelled both ways. RF/SVM assert `classes_ == [0, 1]` before reading `predict_proba[:, 1]`.
   - **`identity`** (W-15, `bin/features/identity.py`, replaced the 512-dim random `dummy`): a one-hot slot per Pfam family of the sorted vocabulary = membership families of the database's train ∪ validation; a pair is the sum of its two sides (same-family pair 2.0, an unseen side nothing, both unseen zeros), interaction layout in both orientations, gzip'd (D-W15-3). It measures what family identity alone explains; on a family-disjoint test split (`minimal_leakage`) every test vector is zero. `FEATURE_EXTRACTION_ONE` stages `train.sqlite3` + `validation.sqlite3` as `vocab/*` inputs of their own (`vocabulary_features` in `PER_DB_BENCHMARK`; a directory input is hashed by the directory's own metadata, so an edited child file would leave a stale vocabulary cached) and passes them as `--vocabulary_db`; `extract_features.py` fails unless the stems equal the module's `VOCABULARY_SPLITS`, and rejects `--vocabulary_db` for any other encoder. Attrs: `layout`, `vocabulary_size`, `vocabulary_sha1` (sha1 of the accessions joined by `\n`), `vocabulary_splits`, `n_pairs`, `n_pairs_both_known`, `n_pairs_one_unseen`, `n_pairs_zero`. The loader (`machine_learning.vocabulary_digest`) requires them for a feature whose module declares `VOCABULARY_SPLITS`, checks `vocabulary_size` = width, and the width registry also holds the sha1, so splits with different vocabularies fail. `model_parameters.json` gains `feature_digests` (only when a feature has one, so every other model's file is unchanged) and test scoring (also `--predict-only`) fails unless each test file's digest equals it. In `params.large_features` (D-W15-4, provisional): dense, ~V floats per pair. Out of `_all` / `_all_seq`.
   - `SVM` (`bin/svm.py`, opt-in via `machine_learning_models`) is `make_pipeline(StandardScaler(), SVC(probability=True))` — cuML on GPU, sklearn only under `--allow_cpu` for the whole run. Kernel SVC at the real `_all` scale (~283k × 7.6k train rows, with Platt's internal CV) has not been measured; `random_state` reproducibility of cuML's probabilities is unverified.
4b. **Degree baseline** (W-15, `DEGREE_BASELINE` / `bin/degree_baseline.py`, per (db, seed), `process_single`): score(A, B) = deg(A) × deg(B), deg(F) = distinct positive DDIs of F in `DDI/train.csv` (undirected; a same-family positive adds 1 once; unseen 0), on every DDI of each `<split>.csv`, canonical, one row per DDI: `domain_a, domain_b, true_interaction (int8), predicted_probability (float32 = the integer product)`, no label columns. Fails on a pair labelled both ways and on a product > 2^24 (float32 stops being exact; EVAL_ONE casts to float32). Never inverted; ties get half credit in ROC AUC. Published to `<db>/baseline_output/degree_baseline/`. Its output joins `scored_ch` before the shared `flatMap` as `(meta, pred, [])`; `meta.ranking_only` is merged into `m_eval` only when set, so no model's EVAL_ONE/ENRICHMENT hash moved. Cardinalities (M = ML models × combos, S = seeds): the EVAL_ONE group is `(M + 1) × S`, ENRICHMENT stays `M` (the baseline is filtered out: its scores are products, `1 - p` means nothing); the "Nothing to benchmark" guard counts real models only, and a variant whose EVALUATION group holds only `degree_baseline.seed*.json` fails ("every model failed").
5. `GRAPH_MODEL` (KGIDDI, DDIParsimony, KGIDDI_RANDOM) scores every test split. **As shipped they do not train:** each `assets/<model>.json` carries an `optimized` block, which makes `kgiddi.py` / `ddiparsimony.py` skip the parameter search, never read `train.sqlite3`, and build the model from the test split's own database. This and the other open graph-model findings are collected in `GRAPH_MODELS.md`. Output goes to `results/<db>/graph_models/<model>/predictions_<variant>.parquet`, pair-canonicalised through `load_data_gm.canonical_pair` like every other prediction file. All three build their interactome from PPIs at or above `params.ppi_score_cutoff` (STRING `combined_score`, default 400 = STRING's "medium confidence"). It is one pipeline-level param, not a per-model JSON key, because the models are compared against each other and must see the same network; `run_graph_models.py --ppi_score_cutoff` overrides a model JSON's own value, and `DEFAULT_PPI_SCORE_CUTOFF` in `bin/load_data_gm.py` is the last resort.

   DDIParsimony's LP relaxation (`ddiparsimony_functions.compute_lp_score`) poses its constraint matrix **sparse**. It used to build one dense `np.zeros(len(domain_pairs))` row per kept PPI and stack them — an `(n_constraints × n_domain_pairs)` float64 matrix whose rows hold at most `|domains(p1)| × |domains(p2)|` nonzeros. Measured at 8k constraints × 20k pairs that is 1.2 GiB of matrix and 2.5 GiB of process peak, versus 0.6 MiB / 62 MiB sparse — and `compute_random_x_matrix_parallel` has every pool worker build one concurrently, which is what OOM-killed the workers and surfaced as `BrokenProcessPool`. HiGHS converts its input to sparse CSC internally either way, so the LP is identical; verified bitwise-equal `res.fun` and `res.x` against the dense form. That pool also runs under **spawn** with an `initializer`, so the adjacency matrix and domain maps are pickled once per worker instead of once per each of the 1000 submissions, and `random_x_matrix` is float32 — the workers only ever returned float32. Raising it is not free: a split database holds only its own proteins' interactome, so at 900 `minimal_leakage/test_balanced` (old variant name) kept 2 of 254 PPIs, which collapsed KGIDDI's union-find into one cluster and left chi2 with no outside stratum to contrast against. `load_data_gm.load_ppi` **coerces the score to numeric and fails if any row will not coerce** (a NULL included). It was not numeric in the databases of 2026-09-02: domainsplit declared `protein_protein_interaction.score` with no type (BLOB affinity, stores whatever class it is handed) and its `insert_ppi.py` bound the raw string it split out of STRING's links file, so pandas read an `object` column and `score >= cutoff` raised `'>=' not supported between instances of 'str' and 'int'`. domainsplit types the column `REAL` and parses the score now, so a fresh database needs nothing from the check — it stays for databases already on disk, which do not get retyped. Failing rather than dropping is deliberate: an unparseable score cannot pass any cutoff, so tolerating it would score a quietly smaller interactome.

It sorts rows by canonical key and records `pair_set_sha1`; the pairwise significance table compares only models with identical pair sets, Holm-adjusted within the dataset. Duplicate source rows across the two orientations of `<split>_sources.csv` are dropped with a warning; a pair with several *different* sources is legitimate and keeps all of them without multiplying the global metrics. ### The domain key

Every domain is named by its **Pfam accession** (`domain.pfam_id`) throughout: the DDI CSVs, the feature HDF5 group names, the `domain_a`/`domain_b` columns of every `predictions_*.parquet`, and `eval_one.py`'s per-source join.

Every `predictions_*.parquet` is also **canonically ordered** — `domain_a <= domain_b`, one row per DDI. A DDI is undirected, so the emitted orientation should not depend on which one a model's internal iteration produced. `bin/load_data_gm.canonical_pair` is the rule; `machine_learning._aggregate_to_ddi_level` applies the same comparison inline. Plain string comparison is correct here only because a Pfam accession is `PF` + a zero-padded five-digit number, so lexicographic and numeric order coincide — it would not hold for a bare integer id.

Instance ids (`domain_protein_map.instance_id`) are domainsplit's `<family>_<accession>_<start>_<end>`, i.e. also stable across runs; only the `'r'||rowid` fallback for a NULL id (`embeddings.INSTANCE_KEY_SQL`) is local to one database file, and a membership pair can never reference one.

On the ML side that canonicalisation also **merges the two orientations**. `load_embedding_data` adds both `(A, B)` and `(B, A)` to `labeled_domain_pairs`, deliberately: the feature vector is `concat(emb_a, emb_b)`, so without it the model learns an order-dependent function of an undirected relation. Grouping on the raw orientation carried that augmentation into the output — two rows per DDI, so every metric counted each one twice and `n_scored` came out at twice the split's `n`. Merging makes the prediction the mean of the two orientations, i.e. symmetric, and leaves one row per DDI.

Not `domain.id`. That is a **per-run surrogate integer**: domainsplit's `SUBSET_SPLIT_DB` copies it verbatim and `PRUNE_UNREPRESENTED_DDIS` deletes without renumbering, so the same integer names a different domain in the next run and a report keyed on it cannot be compared between runs — which is the entire point of the report. `domain` is `UNIQUE(pfam_id)` with `id INTEGER PRIMARY KEY`, so the two are in bijection *within* a database and the swap loses nothing. `DDI_EXTRACTION` fails if any `pfam_id` is NULL, because that would merge unrelated domains into one row rather than error.

This closed a total join failure. The graph models never went through the CSVs — `bin/load_data_gm.py` reads the split database directly and has always joined `domain` for `pfam_id` — while `DDI_EXTRACTION` emitted surrogate ids, so *every* graph-model pair missed `eval_one.py`'s join against `<split>_sources.csv` and the report showed one quiet `unknown` row holding the whole test set. A non-empty unmatched set is now fatal there, naming examples; the surviving `unknown` row means only NULL provenance in the database.

### Published embeddings

domainsplit publishes one `<model>_domain_embeddings.h5` per **run** under `--embeddings`, keyed `h5[pfam_id][instance_id]`. It is per-run, not per-split: it holds every domain the run saw and each split database is a subset of that, so one file serves train, validation and every test split. `--embeddings` may be omitted when `--input` is a directory — domainsplit publishes `embeddings/` as a sibling of `databases/`, so the pipeline derives it one level up and only errors if that directory does not exist (`embeddingsDir()` in the subworkflow). A samplesheet input still requires it explicitly: its rows can point at several runs.

Nothing raises when a file does not fit. `machine_learning.load_embedding_data` **skips** every pair and instance combination it cannot resolve, so an ill-fitting file produces zero training rows, which looks exactly like a database that holds no data. Assert the join resolves; never assume it. Two places do:

- `bin/verify_embeddings.py` (run by `VERIFY_EMBEDDINGS`, before any model trains) measures, for each split in `meta.splits`, the fraction of `ddi_split_membership` instance **pairs** whose two sides are both in the HDF5 with all-finite vectors — exactly what the loader will look up — and fails under `params.min_embedding_coverage` (default 0.95). It also logs DDI-level coverage and missing / non-finite counts, and rejects a file still declaring the retired `key_layout = {domain_id}/{instance_id}`. It used to count every `domain_protein_map` instance by key presence alone: at the old 0.5 that let ~25% pair coverage through (pair ≈ instance²), and an all-NaN file scored 100%. Because NN/RF consume its output, an unverified file cannot reach a GPU.
- `machine_learning.load_embedding_data` tallies per-feature hits and raises naming the feature when one resolves no domain pair at all, or when every domain pair resolves but no instance pair does. Partial resolution is logged per split, not fatal.

The same blind spot holds for **structures**: one `structures.h5` serves every database of a run, keyed by Pfam accession and instance id, so a samplesheet mixing domainsplit runs (or an explicit `--structures` from another run) can silently reuse a foreign run's complex for matching keys. Documented, deliberately not guarded, like embeddings.

Note what the coverage check cannot do — this inverted when the key changed. Pfam accessions are **stable across runs**, so it catches a wrong or stale *export* (wrong dataset, made before domains were added, truncated) but **not a foreign run** over the same domain universe: that resolves ~100%. There is deliberately no guard for it. `params.domainsplit_run` used to be one and was removed: with `--embeddings` derived from `--input`'s own directory the right pairing happens by construction, and for a samplesheet run — or an explicit `--embeddings` — pointing at the matching run is the caller's job. Getting it wrong shows up as a coverage failure only if the two runs also disagree on domains.

### Numeric params on the command line

`main.nf` opens with a typed `params { }` block declaring `ppi_score_cutoff: Integer`, `min_embedding_coverage: Float`, `allow_cpu_ml: Boolean`, plus the nf-core boolean flags (`validate_params`, `monochrome_logs`, `plaintext_email`, `help_full`, `show_hidden`, `version`) — **types only**; the defaults stay in `nextflow.config`. The boolean flags are there because `--validate_params false` otherwise arrives as the String `"false"`, which is truthy, and left validation on (verified). `help` stays undeclared: it is a string-or-boolean union. So does `seeds`: a comma list arrives as a String anyway, `seeds: 42` in a `-params-file` is an Integer, and `parseSeeds()` takes both (the schema types it `["string", "integer"]`).

It is there because Nextflow's v2 (strict) parser, the default since 26.x, stopped inferring types for command-line parameters. `--ppi_score_cutoff 900` arrives as the String `"900"` and nf-schema rejects it against `"type": "integer"` with `Value is [string] but should be [integer]`. A typed declaration makes Nextflow coerce before validation. Add any new numeric or boolean param here, or it cannot be overridden from the CLI.

Two things that look like the fix and are not, both tested:

- `validation.lenientMode = true` only widens the *other* direction — it lets an integer satisfy a `string` type. The option is read (`Set 'validation.lenientMode' to true` in the log) and the run still fails.
- `NXF_SYNTAX_PARSER=v1` does restore type inference, by reverting to the retired parser. Not a fix, a postponement.

Use `Float`, not `Double`/`BigDecimal`/`Number`: those reject the String outright (`Parameter 'f' with type Double cannot be assigned to 0.8 [String]`) instead of coercing it. A `-params-file` (YAML/JSON) preserves types on its own and never needed any of this.

**Only the entry script's declarations count.** A `params { }` block inside an included script is ignored, so a pipeline that embeds this one as a subworkflow would have to repeat the declarations in its own `main.nf`. The same fix is in `daisybio/domainsplit` and `ppi-splitting-pipeline`; domainsplit has to declare the ppi-splitting params it inherits through `includeConfig` for exactly this reason.

### Reproducibility

The pipeline is bit-reproducible for a given commit + input + `--seeds` on the tested setup (CPU backend, pinned container tags, `-profile test,docker --allow_cpu_ml true`), and `nf-test` asserts it by snapshotting model and prediction contents. Anything that draws from an RNG must take a `--seed` (one value of `params.seeds`), call `determinism.seed_everything`, and use `derive_seed` for work inside a process pool. Two traps worth knowing:

- Never iterate a `set`/`dict` of strings where the order affects output, even with `PYTHONHASHSEED` fixed — sort it. The fixed salt makes it reproducible, but the sort makes it obvious.
- joblib/`ProcessPoolExecutor` workers inherit no RNG state. Reseed inside the worker (skorch's `on_train_begin`, or a `seed` argument), and never key a result's position on completion order — `compute_random_x_matrix_parallel` used to number rows by `as_completed`. skorch is worse than it looks: `initialize()` draws the weights *before* `on_train_begin` fires, so the callback alone is not enough (hence `SeededNeuralNetBinaryClassifier`).
- **A function that draws must take the seed, not reach for the global RNG.** `compute_lp_score` drew its reliability mask from `np.random.rand()` while running in a pool, and was reproducible only by accident: under fork every worker inherited one shared RNG state, and the 6-point reliability grid happened to be smaller than the worker count, so each worker ran at most one task. `seed` and `rng_token` are now keyword-only *and* have no defaults, so a caller that forgets raises `TypeError` instead of quietly randomising a benchmark. `rng_token` names what is being scored (`train_grid:<r>`, `test_eval:<variant>:<r>`, `random_x:<i>`): two calls meant to reproduce each other pass the same token — which is how the `avg_x_vec_*.npy` written beside `pw_scores_*.json` now actually corresponds to those scores, where before the rerun drew a fresh mask and saved a vector the scores did not come from.
- **Deriving per item beats drawing in a loop.** The retired `dummy` encoder (replaced by `identity` in W-15) first drew from the seeded global RNG once per row, so each vector's value depended on its *position* in a query with no `ORDER BY`; it was fixed to derive `derive_seed(seed, "dummy", domain_key, instance_key)` per instance: same vector for the same pair regardless of row order or how many rows precede it. Same rule for any future sampling encoder — which must also be added to `seeded_features` in `PER_DB_BENCHMARK` (empty today; the mechanism stays), or every seed silently reuses the primary seed's vectors.
- **One RNG parameter, one spelling, and it has to be *wired*.** `params.seeds` (default `'42'`, a comma list, parsed and validated at launch by `parseSeeds()` in the utils subworkflow: integers 0..2^31−1, no empty token, no repeat) is the only seed parameter the pipeline has; every entrypoint takes one value of it as `--seed`, from `meta.seed` — never `params.seed`, which no longer exists. `eval_one.py` used to call its own `--bootstrap_seed`, defaulted to 42, and no module passed it — so the seed never reached the bootstrap CIs. Renamed and wired. A second seed parameter, or a flag spelled differently, is the bug.
- **Several seeds** (`--seeds 42,43`, W-6). The first is the **primary seed**. Seed-dependent tasks fan out per seed: `NEURAL_NETWORK` / `RANDOM_FOREST` / `SVM` (`.combine(Channel.fromList(seeds))`, `meta.seed`), `DEGREE_BASELINE` (identical scores per seed; the rows are evaluation replicates whose bootstrap differs, D-W15-2), `FEATURE_EXTRACTION_ONE` for the features in `seeded_features` (`[]` since W-15: no encoder draws; every encoder runs once with the primary seed and its file carries seed null), and `EVAL_ONE` (the model's own seed, output `<model>.seed<N>.json`, `seed` key in the JSON). Each model task would stage only its own seed's copy of a seeded feature (`comboFiles(..., seed)`). Graph models and `ENRICHMENT` run on the primary seed only (enrichment's status block says so in a multi-seed run). `EVALUATION` gets `--seeds`: with more than one, curves, pairwise tests, coverage, by-source accuracy and the W-11 source panels (cross-source AUC matrix, score box plots; `EVAL_ONE` computes them for every seed) are the primary seed's (descriptions say so), the two metric tables carry the **mean over seeds** (+ `Seeds` k/n, `ROC AUC SD`, `PR AP SD`, `ROC AUC min–max`; the CI strings stay the primary seed's bootstrap CI), and two more blocks appear, `seed_variance` (one row per (model, seed), also `seed_metrics.json`) and `order_agreement` (AUC(a) > AUC(b) in k/n seeds — a count, never a significance verdict, CR-17.6). `combine_eval.py` appends `± SD over n seeds` to the heatmap CI cells. Publish paths gain `seed<N>/` (`<db>/{nn,rf,svm,baseline}_output/seed<N>/…`, `<db>/data/seed<N>/` for a seeded feature) and the tags `_seed<N>`, both set in `conf/modules.config` only, so neither reaches a task hash: adding a seed reruns only the new seed's tasks plus the reports. **With one seed every path, file and byte is what it was before W-6** (nothing switches on below two seeds); use a fresh `--outdir` when changing the number of seeds, or the flat and `seed<N>/` copies sit side by side.
- A model can be bit-identical while something derived from it is not. sklearn's `RandomForest.predict_proba` parallelises the per-tree sum, so with `n_jobs=-1` the `.pkl` matched run to run but the tuned threshold in `model_parameters.json` did not. Fitting is deterministic; prediction is where the reduction order leaks. The CPU path is therefore `n_jobs=1`.
- **Nextflow's own ordering is a reproducibility surface.** `groupTuple()` and `collect()` emit in task-completion order. If that list becomes a command-line argument order, it reaches the output: MultiQC writes its JSON in the order it was fed, so `--per_model_metrics` had to be sorted. Sort every grouped list before it reaches a script — it also stabilises the task hash for `-resume`.

Do not re-add entries to `tests/.nftignore` to make a snapshot pass: that hides real regressions. Regenerate the snapshot instead, and only for a change you can explain.

### Report ordering

`params.mqc_order` is a comma-separated list of dataset (run label) names — `random_uniform_1_1,minimal_leakage_hrni_uniform_1_10,external_test`. A *dataset* is one (database, test variant), the same label `runLabel()` builds. It drives three things, all via the helpers in `bin/eval_multiqc_functions.py` (`parse_dataset_order`, `resolve_dataset_order`, `sort_by_dataset`, `order_dataset_keys`):

- the MultiQC section order of the blocks that exist once per dataset (`db_database_analysis_<ds>`, `model_eval_metrics_<ds>`);
- the tab/series order inside blocks that carry every dataset (combined ROC/PR line graphs, the by-source bar graph);
- the column order of the AUC/AP heatmaps and their CI tables.

A requested (or repeated) name that exists in no dataset is a **hard failure at launch** (`validateDatasets()`), with `combine_eval.py` keeping its own check as a backstop. Only `COMBINE_EVAL` receives `--mqc_order`; a per-dataset report holds one name, so passing it to `EVALUATION` only reran every evaluation when the order changed. A dataset in the data but missing from the list **warns** and is appended alphabetically after the ordered ones; dropping it silently would hide a whole database. Left unset, everything is alphabetical (never input order — the report has to be a function of the names alone to stay reproducible).

The degree, betweenness and clustering-coefficient box plots are gone, in both the per-dataset and combined reports. Betweenness and clustering were never computed (both returned a hardcoded `[1..10]`, the real `nx` calls commented out because they do not finish on a PPI graph this size), and the degree distribution answered a question the node/edge counts in `database_analysis` already cover. `analyse_interaction_network` now returns node and edge counts only.

### Adding things
- **New ML model:** not picked up automatically. Add `assets/<Name>.json` (must include `model_name`, `data`, `search_parameters`, `model_parameters`), a `bin/<name>.py` subclassing `machine_learning` (template: `bin/new_model.py`), a process under `modules/local/`, its wiring in `per_db_benchmark` (which hardcodes `neural_network` / `random_forest`), and its name in `validateModelParams()`'s known list.
- **New feature encoding:** add `bin/features/<name>.py` and append `<name>` to `params.machine_learning_features` in `nextflow.config`. One built against a vocabulary of other splits declares `VOCABULARY_SPLITS`, takes `vocabulary_dbs`, writes `vocabulary_sha1` / `vocabulary_size`, and goes into `vocabulary_features` in `PER_DB_BENCHMARK`. If it draws from the RNG, add it to `seeded_features` in `PER_DB_BENCHMARK`, or every seed reuses the primary seed's vectors. Append to `params.large_features` if it needs GPU/big memory. A sequence encoder should expose `SEQUENCE_QUERY` and `MIN_SEQUENCE_LENGTH` and use them itself, so `PREFLIGHT` cleans exactly what it will read.
- **New structure feature:** add `bin/features/<name>.py` defining `encode(cx, **params)` and `extract_features = structure_utils.make_extractor(encode)`, then append `<name>` to `params.machine_learning_features_structure`. A parameterised variant needs only an entry in `assets/feature_variants.json`.
- **New published feature:** no Python file. Append `<name>` to `params.machine_learning_features` *and* `params.published_features`, and drop `<name>.h5` (or `<model>_domain_embeddings.h5`) into `--embeddings`. If it was computed with structure input, append it to `params.structure_informed_features` too, or it lands in `all_seq`.
- **Feature combos:** built in `PER_DB_BENCHMARK` as `[id, features]` — one singleton per feature (id = feature name), `all` (every feature except `identity`) and `all_seq` (`all` minus `machine_learning_features_structure` and `structure_informed_features`), each only with ≥ 2 features, and `all_seq` only when it differs from `all`. `meta.combo_id` names the output dir (`<model>_<combo_id>`), task tag, report entry and the EVALUATION group size; a feature may not be called `all` or `all_seq` (duplicate ids fail). `eval_multiqc.is_structure_assisted` matches the suffix `_all`, so `_all_seq` is never marked structure-assisted.
- **Skip stages:** `--skip aacomp,kgiddi` (comma-separated; matches feature, ML model or graph model names; an unknown token fails at launch). With every ML model skipped, feature extraction and `VERIFY_EMBEDDINGS` do not run at all.

### Profiles
- No profile: local executor, host Python (there is no `standard` profile).
- `conda` / `mamba`: environments from `environments/*.yml`.
- `apptainer` / `singularity` / `docker`: container engine, with a 2 h pull timeout (the GPU image is large).
- `gpu`: adds `--nv` / `--gpus all`; on a cluster it is also the profile the institutional config keys on to send `process_gpu` tasks to the GPU queue.
- `test_full`: the pipeline defaults (every sequence feature, `identity` and `esm3_structure_embeddings` included; structure features off; NN/RF/SVM; graph models off) on the final domainsplit `databases/` directory (`all_species_reviewed_without_homomers`) on the cluster.
- `test`: minimal SQLite triplet under `tests/data/`. Features are `aacomp,identity,esm3_embeddings` — one cheap extracted encoder, the vocabulary encoder, and one published embedding (no seeded encoder is covered: none exists), so the singleton and all-concat combos each mix extracted and published sources. With the two structure features below, `_all` = `aacomp,esm3_embeddings` + both structure features and `_all_seq` = `aacomp,esm3_embeddings`, so both concatenations run (7 combos × 3 models per database). The fixture has no `esm3_structure_domain_embeddings.h5`, so the profile sets `structure_informed_features = 'none'`. `graph_models = ''`: the graph models are deliberately **not** covered, so changes to `ddiparsimony.py` / `kgiddi.py` / `load_data_gm.py` carry no snapshot signal and have to be argued for by hand.
  The test profile also runs `svm`, the structure features `sasa_residue` (chain-ordered, reads the SASA cache) and `k_closest_distance_5k` (a variant) from `tests/data/structures/structures.h5`, and enrichment from `tests/data/metadata/`. The fixture has partial structure coverage on purpose (one positive missing one pair, one negative missing all) and one same-family pair per split.
- `daisybio`: site-specific defaults from nf-core/configs. `daisybio.config` sets `cleanup = true`, so pair it with `keep_work` if you want `-resume` to work.

The only tracked samplesheet is `assets/samplesheet_example.csv` (the in-repo fixture; the old cluster sheets were deleted). Run-specific values (`--input`, `--outdir`, `--mqc_order`) live in an untracked `-params-file`, not in `nextflow.config`. `test_full` points at the current domainsplit output on the cluster.
